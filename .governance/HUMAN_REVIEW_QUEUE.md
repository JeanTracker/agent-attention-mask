### HRQ-006: 외부 앱에서의 세션 모니터링·설정과 `claude` shim 설치 (2026-09-16)
- **사용자 방향 (이 세션에서 직접 지시)**: (1) 터미널에서 `claude`를 칠 때 amask가 개입하도록 **PATH에 등록하는 서브커맨드를 amask가 제공한다**, (2) **amask의 모든 설정을 세션별로 외부 앱에서 할 수 있게 한다**. 아직 논의 단계이고 구현은 시작하지 않았다.
- **지금 사실**:
  - 설정면은 env 3개(`AMASK_IDLE_SILENCE`·`AMASK_HOOK_STALL`·`AMASK_OVERLAY_DELAY`)뿐이고, `cli.py`의 **모듈 상수로 import 시점에 한 번** 읽는다. 세션별·런타임 변경은 이 값들을 `Runner` 인스턴스로 내리는 리팩터가 선행된다.
  - 세션 식별 키는 이미 있다 — FIFO 이름이 `amask-hooks-{pid}.fifo`이고 훅 페이로드의 `session_id`도 `amask-hook`의 `KEEP`에 들어 있다. 제어 소켓을 같은 규칙으로 두고 토큰 검증을 D-030 방식으로 재사용하면 표준 라이브러리 안에서 끝난다(D-006 유지).
  - 러너가 아는 상태의 대부분은 훅 채널에서 온다(D-025). 모니터링만이면 러너에 붙지 않아도 되고, 러너 고유 정보는 "지금 덮여 있는지"와 `q` 억제 여부뿐이다.
  - 외부 앱 자체는 이 레포에 들어올 수 없다 — 제약이 "외부 GUI 프레임워크 의존 금지, 순수 터미널 CLI"다. amask는 채널만 제공한다.
- **결정이 필요한 것**:
  1. **외부에서 바꿀 수 있는 설정의 집합.** D-036은 4번째 노브(`IDLE_HINT_AFTER`)를 의도적으로 거부하고 "README 「타이밍 조정」은 상태를 결정하는 세 상수의 자리"라고 못박았다. "모든 설정"은 그 절제를 다시 여는 것이다. 제안: 세 상수 + 명령 3개(`skip`/`wake`/`cover`)로 한정하고, 그 이상은 항목별 D를 받는다.
  2. **적용 시점** — (a) 다음 턴부터, (b) 즉시 라이브 적용, (c) 설정 파일에 써두고 다음 세션부터. (b)는 오버레이가 켜진 채 임계값이 바뀌는 경우의 정의가 필요하다.
  3. **외부 `cover` 명령을 허용할지.** `_hold_until`과 SC-002는 "사용자가 키보드 앞에 있다"를 전제로 덮기를 미룬다. 외부에서 덮으라고 부르는 것은 그 전제와 충돌하므로 규격 판단이다. 외부 입력(프롬프트 전송)은 더 나아가 D-008의 근거("덮인 동안 바이트를 전부 버리므로 `q`의 비용이 0")를 깨므로 별개 항목으로 둔다.
  4. **shim의 P-101 긴장.** 러너가 사용자 환경(PATH, rc 파일)에 쓰는 것은 "단순 시각적 래퍼"에서 벗어난다. 사용자가 이 방향을 택했으므로 채택 자체는 결정됐고, 남은 것은 기록 형태(전용 D 항목)와 되돌리는 방법(`uninstall`)이다.
  5. **재귀 위험** — PATH의 `claude`가 `amask claude`를 부르면 `Runner`가 `argv[0]`을 PATH로 다시 찾아 무한 재귀한다(`main()`의 비-tty 분기 `os.execvp`도 같다). shim은 설치 시점에 실제 바이너리 절대경로를 박거나 env 가드를 둬야 한다. `_with_hooks`가 `basename(argv[0]) == "claude"`를 보므로 절대경로를 넘겨도 훅 주입은 유지된다.
- **왜 혼자 확정하지 않는가**: UX 규격 변경이고 1·3번은 SC·D 항목(SC-002, D-008, D-036)에 직접 걸린다. 5번과 재귀 가드는 구현 판단이라 확정 후 내 재량으로 처리한다.
- **부분 종결 (2026-09-17)**: 1번(세 상수로 한정)·2번(메모리 즉시)·`status`의 프롬프트 노출(포함)·`skip`의 수락 조건(턴 진행 중)을 사용자가 결정했고 D-039로 구현했다. **남은 것은 3번(외부 `cover`)과 4·5번(shim)이다.** shim은 사용자가 "amask가 설치하는 서브커맨드" 방향을 택했으나 아직 구현 전이고, PATH·rc 파일에 쓰는 것이므로 실제로 심기 전에 확인을 받는다.

## HRQ-005: CI에서 SC-002 지연 게이트를 얼마나 느슨하게 둘 것인가 (등록 2026-09-22)

첫 CI 실행(35680927710)에서 macOS 잡 3개가 지연 단정으로 떨어졌다 — SC-002 재렌더링 0.268초(예산
0.2), wake 후 걷히기 t=3.120(0.1초 기대). 같은 코드가 로컬 macOS에서는 전부 통과한다. 공유 러너의
CPU가 남과 나뉘어 있고 그 위의 측정치는 제품 지연이 아니다.

당장은 D-049로 **예산 숫자를 그대로 두고 배수만** 주었다 — `harness.budget()`이
`AMASK_TEST_SLACK`(기본 1.0)을 곱하고, CI 워크플로가 `3`을 선언한다. 개발자 기계는 슬랙 없이 돈다.

**혼자 확정하지 않는 부분:**

1. **배수 3이 맞는 값인가.** 관측치는 0.268/0.2 = 1.34배, 0.12/0.1 = 1.2배다. 3은 여유를 크게 둔
   값이고, 그만큼 실제 회귀도 통과시킨다. 2로 줄일지, 관측을 몇 번 더 모아 정할지.
2. **macOS 잡을 비차단(`continue-on-error`)으로 둘지.** 지금은 차단이다. 실측이 전부 macOS에서
   나온 프로젝트라 비차단은 아깝고, 차단이면 러너 상태로 빨간불이 켜진다.
