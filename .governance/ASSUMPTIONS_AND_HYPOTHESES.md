# ASSUMPTIONS & HYPOTHESES

* **A-001 (Assumption)**: 타깃 환경은 macOS 기반 iTerm2이며, xterm-256color 호환 ANSI 제어 시퀀스를 완벽히 지원한다.
* **A-002 (Assumption)**: 실행 대상 에이전트는 표준 POSIX PTY 인터페이스를 통해 명령을 주고받는다.
* **H-001 (Hypothesis)**: PTY 버퍼에 일정 시간(예: 300~500ms) 동안 새로운 출력이 없고 커서가 대기 중이면 '사용자 입력 대기 상태'로 신뢰성 있게 판정할 수 있을 것이다.

## 검증 결과 (2026-09-07, Cycle 1)

* **H-001 → 검증 완료 (VALIDATED)**. `tests/tap_agent.py`로 실제 `claude`의 PTY 출력을 타임스탬프와 함께 측정:
  * 작업 중: 청크 71개, 중앙 간격 0.105s, **최대 무음 0.232s** (스피너 리드로우가 계속 흐른다)
  * 유휴 프롬프트: **완전 무음 4.93s**, 권한 대기 구간 15s 전부 무음
  * → 바이트 무음이 "사용자 대기" 신호로 신뢰 가능. 임계값은 작업 중 최악값의 약 2.6배인 **0.6s**로 확정. 단, 커서 위치가 아니라 무음만으로 판정하므로 "마지막 바이트가 개행이 아님" 조건은 불필요해 채택하지 않았다(실측에서 유휴 시 마지막 청크가 개행으로 끝나지 않아 판별력이 없었다).
  * 오탐 방지 장치: 에이전트가 **최초 출력을 낸 뒤에만** 유휴 판정을 무장한다(느리게 기동하는 에이전트 보호).
* **A-003 (Assumption, 신규)**: 복원 가능한 스크롤백 길이는 iTerm2의 스크롤백 라인 제한에 종속된다. 러너는 로그 전량을 플러시하지만, 터미널 설정보다 긴 로그의 앞부분은 터미널이 버린다. 러너 통제 범위 밖.
* **A-004 (Assumption, 신규)**: 오버레이 중 창 크기가 변경되면, 이후 플러시되는 로그는 **변경 이전 폭 기준으로 포맷된 상태**로 복원된다. PTY에는 새 크기를 즉시 전파하지만 이미 버퍼에 쌓인 바이트를 재포맷하지는 않는다. Cycle 1 범위 밖으로 기록만 함.
* **A-005 (Assumption, 신규)**: P-103 보장은 iTerm2 프로파일의 **"Save lines to scrollback in alternate screen mode"가 꺼져 있음**(기본값)을 전제한다. 이 옵션이 켜진 프로파일에서는 대체 화면 내용도 스크롤백에 저장되므로 매트릭스 잔상이 남는다. 러너가 제어할 수 없는 터미널 설정이다.
* **H-001 재측정 (2026-09-08)**: 최초 검증은 12초 남짓의 짧은 구간을 재어 "작업 중 최대 공백 232ms"로 결론냈다. 80초짜리 실제 응답 전체를 다시 재니 **최대 공백 807ms**였다 — 짧은 표본이 분포의 꼬리를 놓쳤다. 임계값은 1.5초로 상향(D-023). 타이밍 상수를 정할 때는 대표 구간이 아니라 **가장 긴 실제 작업 전체**를 재야 한다.

## 검증 결과 (2026-09-09, Ghostty 병행 관측)

* **A-005 재검증 → 전제 오류 (기본값 주장 무효), 결론은 유지되지만 근거가 다르다**. 실제 tty에서 프로브를 돌려 iTerm2 3.7.0과 Ghostty 1.3.1을 같은 증거로 비교했다.
  * iTerm2 프로파일에 `Scrollback in Alternate Screen` 키가 없다 = **내장 기본값 상태**. 그 상태에서 대체 화면을 개행으로 스크롤시키면 상단에서 밀려난 줄이 **스크롤백에 저장된다**(rows=32, 96줄 중 각 랩 주기의 1행 3줄 확인). Ghostty는 동일 조건에서 0줄.
  * 따라서 A-005의 "(기본값)"은 틀렸다. 안전한 기본값은 존재하지 않으며, iTerm2는 기본적으로 대체 화면의 스크롤아웃을 저장한다.
  * 그럼에도 실 러너는 양쪽 터미널에서 P-103을 만족했다. 이유는 터미널 설정이 아니라 렌더러 속성이다 — `rain.frame()`·`hud.render()`는 `ESC[row;colH` 절대 좌표와 글리프만 쓰고 개행을 내지 않으며 마지막 행을 넘지 않는다. `script(1)`로 방출 바이트를 받아 실측: 오버레이가 실제로 뜬 실행(1049h 1회, rain 9284/10056셀, HUD 97/109회)에서 대체 화면 구간 401KB/441KB에 개행 0개·bare CR 0개·`ESC D` 0개·`ESC[S` 0개. **대체 화면이 스크롤되지 않으므로 iTerm2가 저장할 줄이 생기지 않는다.**
  * → A-005를 "터미널 설정 전제"에서 **"오버레이 렌더 경로는 스크롤을 유발하지 않는다"는 불변식**으로 대체하는 것이 옳다. 이 불변식이 깨지면 iTerm2 기본 프로파일에서 즉시 P-103 위반이 된다. 문구 정정은 스크롤백 정책 안내에 해당하므로 HRQ-003으로 올렸다.
* **A-006 (Assumption, 신규)**: Ghostty 세션의 `TERM=xterm-ghostty`는 시스템 terminfo DB에 없고, Ghostty가 주입하는 `TERMINFO=/Applications/Ghostty.app/Contents/Resources/terminfo`에만 의존한다. 러너는 `TERM`을 건드리지 않으므로 에이전트 자식이 이 값을 그대로 물려받는다. 같은 환경 안에서는 문제없지만 `TERMINFO`가 끊기는 경로(`sudo`, `env -i`, ssh 원격, 일부 런처)에서는 에이전트가 terminfo를 찾지 못한다. 실측: `TERMINFO` 제거 시 `infocmp: couldn't open terminfo file /usr/share/terminfo/78/xterm-ghostty`. 러너 통제 범위 밖이나 A-001("타깃 환경은 iTerm2")이 더는 유일 환경이 아님을 뜻한다.
* **A-005 재검증의 정정 (같은 날, 2026-09-09)**: 위 bullet은 "실 러너는 양쪽 터미널에서 P-103을 만족했다"고 적었으나 **`take_alt=True` 분기에만 해당한다.** 에이전트가 이미 대체 화면을 쥔 `take_alt=False` 분기(D-010, 대화형 `claude`)에서는 iTerm2 기본 프로파일에서 오버레이 1프레임이 스크롤백에 남는다 — 실측 확인. 원인은 개행이 아니라 `exit_overlay`가 보내는 `CLEAR_HOME`의 `ESC[2J`이고, iTerm2의 ED 2는 지우기 전에 화면을 히스토리로 보낸다. 앞선 불변식 검사가 개행·CR·`ESC D`·`ESC[S`만 세고 ED 2를 세지 않아 놓쳤다. 따라서 **"오버레이는 스크롤을 유발하지 않는다"는 불변식만으로는 P-103이 보장되지 않는다** — ED 2도 스크롤백 기입 경로다. 수정 방향은 HRQ-004. Ghostty는 같은 조건에서 깨끗하다.
* **A-005 종결 (2026-09-10)**: 더 이상 전제가 아니다. `ESC[2J`를 오버레이 경로에서 제거하면서(D-037) P-103이 터미널 설정과 무관해졌다 — 오버레이가 내는 바이트에 개행도, 마지막 행 초과 쓰기도, ED 2도 없으므로 대체 화면에서 스크롤백으로 밀려나갈 줄 자체가 만들어지지 않는다. iTerm2 기본 프로파일(해당 옵션 켜짐)에서 실측으로 확인했다: 수정 후 스크롤백에 HUD 4종 0, 레인 셀 0, 러너의 ED 2 방출 0. 대체하는 불변식은 **"오버레이는 스크롤백 기입 경로를 하나도 밟지 않는다"**이고, `tests/test_phase3_overlay.py`가 `TerminalController`를 직접 구동해 이를 고정한다. 남는 것은 러너 밖의 사실 하나 — 에이전트 자신의 `ESC[2J` 재도색은 그 옵션이 켜져 있으면 계속 스크롤백에 쌓인다(실측 82~86 프레임, 러너 없는 대조군과 동일).
