# DECISIONS

* **D-001**: 창 분할 방식 대신 단일 창 '화면보호기(Screensaver) In-Place 오버레이' 패턴 채택 (결정일: 2026-09-07)
* **D-002**: 에이전트와 오버레이 프로세스의 TTY 충돌 방지를 위해 `Virtual PTY Proxy` 구조 채택 (결정일: 2026-09-07)
* **D-003**: 터미널 스크롤백 오염 방지를 위해 `Alternate Screen Buffer` 강제 사용 확정 (결정일: 2026-09-07)
* **D-004**: 매트릭스 종료 시 가상 PTY 누적 로그를 일반 화면에 플러시하여 스크롤백 복원 확정 (결정일: 2026-09-07)
* **D-005**: cmatrix 바이너리 호출 대신 **내장 디지털 레인 렌더러** 채택 (결정일: 2026-09-07)
  * 근거: cmatrix 2.0은 ncurses 기반이라 `initscr()`/`endwin()`이 자체적으로 alt screen(smcup/rmcup)을 토글한다. 러너의 `1049h`/`1049l` 쌍 안에 중첩되면 rmcup이 새어나갈 수 있고, 비정상 종료 시 `endwin()`이 호출되지 않아 매트릭스 글리프가 일반 버퍼에 남는다. P-103은 이를 제품 실패로 규정한다. AGENT_AUTONOMY가 명시적으로 허용한 선택지(AUTONOMOUS).
* **D-006**: 구현 언어를 **Python 3 표준 라이브러리**로 확정 (결정일: 2026-09-07)
  * 근거: 대상 머신에 Go 툴체인 미설치. `pty`/`termios`/`tty`/`select`/`fcntl`만으로 요구사항 전부 충족되어 서드파티 의존성 0개. AUTONOMOUS 범위.
* **D-007**: 로그 버퍼를 링 버퍼가 아닌 **익명 스필 파일**로 구현 (결정일: 2026-09-07)
  * 근거: SC-004는 로그 전량 보존을, CONSTRAINTS는 RAM 50MB 미만을 요구한다. 링 버퍼는 정의상 오래된 출력을 버려 SC-004와 충돌한다. `mkstemp`(0600) 직후 `unlink`하여 fd만 보유 — 에이전트 출력에 흔히 포함되는 인증 토큰이 프로세스보다 오래 남지 못하게 한다(FORBIDDEN 준수). 메모리는 정수 2개만 사용. AUTONOMOUS_WITH_RECORD.
* **D-008**: 깨우기 제스처로 쓰인 입력은 **에이전트에 전달하지 않고 폐기** (결정일: 2026-09-07)
  * 관측된 부수 효과: 마우스 모드 1000은 스크롤 휠을 버튼 4/5 이벤트로 보고하므로, 클릭뿐 아니라 스크롤·트랙패드 관성 스크롤도 깨우기로 동작한다. SC-002의 문구는 "클릭"이지만 사용자 의도 표현이라는 점에서 동일하게 취급한다.
  * 근거: SC-002의 "임의의 키"를 그대로 전달하면 Enter가 빈 프롬프트를 제출하거나 대기 중인 y/n 확인을 승인해 버린다. 깨우기 제스처는 에이전트 입력이 아니다. 추가로 복귀 직후 0.3초간 마우스 리포트 시퀀스만 선별 제거한다(MOUSE_OFF 이후 도착하는 릴리스 이벤트 차단). 시간 제한을 둔 이유는 에이전트가 자체 마우스 트래킹을 켤 수 있고 그것까지 거르면 P-101 위반이기 때문. AUTONOMOUS_WITH_RECORD.
* **D-009**: 오버레이 중에도 에이전트의 **터미널 능력 질의 시퀀스는 통과**시키고, 그 응답은 깨우기로 취급하지 않음 (결정일: 2026-09-07)
  * 한계: 질의·응답 판별은 단일 read 청크 안에서 정규식으로 수행한다. 하나의 응답이 두 번의 read에 걸쳐 쪼개져 도착하면 매칭에 실패해 깨우기로 오인될 수 있다. 관측된 적은 없으며 Cycle 1에서는 기록만 한다.
  * 질의는 실제 터미널로 즉시 통과시키되 **로그에는 넣지 않는다**. 플러시 때 재전송되면 터미널이 두 번째 응답을 보내고, 그 응답이 패스스루 상태에서 에이전트에 키 입력으로 주입되기 때문이다.
  * 근거: 실측에서 `claude`는 기동 시 DA(`ESC[c`) 2회, OSC 컬러 질의 1회를 보낸다. 이를 막으면 에이전트가 터미널 능력을 오판해 SC-005가 저하된다. 질의·응답은 화면에 보이지 않으므로 통과시켜도 P-103과 무관하다. 반대로 응답이 stdin에 도착할 때 키 입력으로 오인하면 기동 즉시 스크린세이버가 꺼진다. AUTONOMOUS_WITH_RECORD.
* **D-010**: 에이전트가 이미 대체 화면을 점유한 경우 **오버레이를 중첩하지 않고 덧그린다** (결정일: 2026-09-07)
  * 근거: 실측상 대화형 `claude`는 기동 13번째 바이트에서 `ESC[?1049h`를 보내고 종료까지 유지하는 전체 화면 TUI다. 그 위에 러너가 `1049h`를 또 보내면 에이전트 화면이 지워지고 `1049`쌍이 불균형해져, 복귀 시 `1049l`로 일반 버퍼에 떨어지며 TUI가 깨진다.
  * 구현: 에이전트 출력에서 `1049h`/`1049l`(및 1047/47)을 추적해 점유 상태를 안다. 점유 중이면 러너는 `1049h`를 보내지 않고 화면을 지운 뒤 레인을 그리며, 복귀 시에도 `1049l` 대신 화면만 지우고 에이전트에게 `SIGWINCH`를 보내 스스로 재렌더링하게 한다(전경 프로세스 그룹 대상, 실패 시 자식 PID로 폴백).
  * 이 경로에서는 스크롤백 오염 위험이 없다 — 에이전트가 연 대체 화면 안에서만 그리기 때문이다.
  * **재렌더링에는 실제 크기 변화가 필요하다.** 크기가 같은 SIGWINCH는 Node의 tty 스트림(따라서 Ink, 따라서 대화형 claude)이 무시한다 — winsize를 다시 읽어 이전 값과 같으면 `resize` 이벤트를 발생시키지 않는다. 실측 결과 신호만 보냈을 때 화면이 복구되지 않았다. 그래서 pty를 한 행 줄였다가 다음 루프 틱(약 60ms 후)에 되돌린다. 즉시 되돌리면 에이전트 핸들러가 실행될 때 이미 원래 크기라 델타를 못 본다(경쟁 상태, 실측 확인). 신호를 직접 보는 에이전트를 위해 `killpg(SIGWINCH)`도 함께 보낸다.
  * **한계 (기록만)**: `exit_overlay`는 `MOUSE_OFF`와 `CURSOR_SHOW`를 무조건 보낸다. 에이전트가 자체 마우스 트래킹을 켜뒀거나 커서를 숨겨뒀다면 깨어날 때 덮어써진다(P-101 경계 사례). 위 재렌더링이 대개 이를 복구하지만 의존 관계로 남는다.
  * **한계 (기록만)**: `1049h`/`1049l` 탐지는 D-009와 같은 청크 분할 제약을 갖는다. 시퀀스가 두 번의 read에 걸치면 점유 상태를 놓쳐 대체 화면을 중첩하게 된다. 실측상 claude는 기동 첫 청크의 13번째 바이트에서 보내므로 발생 가능성은 낮다.
* **D-011**: 오버레이 **지연 진입 + 재진입** 도입, G-001 라이프사이클 2·6번 개정 (결정일: 2026-09-07, **사용자 승인**)
  * 분류: HUMAN_REQUIRED (UX 규격 및 목표 범위) — 사용자가 HRQ-001의 4번 선택지와 HRQ-002 재진입을 함께 승인했다.
  * 규격: 기동 시에는 덮지 않는다. **에이전트가 작업 중이고 사용자 입력이 없는 상태가 `OVERLAY_DELAY`(기본 4초) 지속되면** 덮는다. "작업 중"의 판정은 D-013에서 정밀화되었다. 키·클릭·에이전트 무음·에이전트 종료 중 하나로 복귀하며, 복귀 후 조건이 다시 성립하면 재진입한다.
  * "작업 중"과 "유휴"는 같은 측정의 양면이다 — `IDLE_SILENCE`(0.6초) 동안 출력이 없으면 유휴, 아니면 작업 중.
  * 사용자 입력이 들어올 때마다 진입 타이머를 초기화한다. 사용자가 타이핑 중이면 화면을 덮지 않는다.
  * 수동 복귀 후의 처리는 D-014로 대체되었다(시간 유예 → 사용자 재지시 대기).
  * 최초 출력 이전에는 유휴로 판정하지 않는다. 따라서 아무 출력 없이 오래 도는 빌드 스크립트는 "작업 중"으로 간주되어 정상적으로 덮이고, 종료할 때까지 덮인 채 유지된다.
  * 상수는 환경변수(`AMASK_OVERLAY_DELAY` / `AMASK_IDLE_SILENCE`)로 조정 가능하다. 테스트 스위트는 이를 이용해 압축된 타이밍으로 돈다.
* **D-012**: 에이전트가 대체 화면을 점유한 경우 **숨겨둔 출력을 재생하지 않고 폐기한다** (결정일: 2026-09-07)
  * 근거: 그 출력은 애초에 스크롤백으로 가지 않는다 — 에이전트의 대체 화면 안에서 소비되고 사라지는 프레임이다. 재생하면 숨어 있던 시간만큼의 낡은 화면을 전부 렌더링한 뒤에야 에이전트가 덮어 그리며, 비용이 오버레이 지속 시간에 비례해 늘어난다. 실측: 10초 오버레이에서 328KB를 재생했고 SC-002의 0.2초 예산을 위협했다. 폐기 후 2KB.
  * 따라서 SC-004는 이 경로에 적용되지 않는다. 복원 수단은 플러시가 아니라 D-010의 재렌더링이다.
  * 예외: 오버레이 도중 에이전트가 `1049l`을 보내 TUI를 스스로 떠났다면, 이후 출력은 일반 버퍼용이므로 정상적으로 플러시한다.
* **D-013**: 오버레이 진입 조건을 "출력 있음"이 아니라 **연속 작업 구간(busy run)**으로 판정 (결정일: 2026-09-07)
  * 문제: 사용자 보고 — `amask claude`를 아무 입력 없이 두면 매트릭스가 떴다가 자동으로 닫히기를 반복했다.
  * 원인 (실측): 유휴 상태의 대화형 claude는 **8~10초마다 짧게 리페인트**한다(149B, 59B 관측). 기존 로직은 출력이 한 번이라도 있으면 `IDLE_SILENCE`(0.6초) 동안 "작업 중"으로 판정했으므로, 블립마다 진입 조건이 성립하고 0.6초 뒤 유휴 판정으로 닫히는 왕복이 발생했다.
  * 규격: 출력 사이 간격이 `IDLE_SILENCE` 미만으로 이어지는 구간을 하나의 **busy run**으로 보고, run이 `OVERLAY_DELAY` 이상 지속될 때만 덮는다. 단발 블립은 run을 누적하지 못한다.
  * **busy run은 프로세스 시작 시점부터 시작한다.** 아직 아무 말도 하지 않은 에이전트는 작업 중이기 때문이다 — 실측상 `claude -p`는 작업하는 5.88초 동안 출력이 전혀 없다가 답만 내놓는다. 이 초기화가 없으면 비대화형 모드가 영영 덮이지 않는다(회귀로 실제 발생).
  * 즉 무음의 의미는 모드에 따라 정반대다: 비대화형은 무음이 곧 작업이고, 대화형 TUI는 무음이 대기다. 두 경우를 "말한 적 없으면 작업 중, 말했다가 멈췄으면 대기"라는 한 규칙으로 통합했다.
* **D-014**: 수동 복귀 후에는 **사용자가 다시 작업을 지시할 때까지 재진입하지 않는다** (결정일: 2026-09-07)
  * 사용자 지시: "사용자가 matrix 화면에서 아무키나 누르는 경우 수동으로 닫아. 다시 열리는 경우도 마찬가지로 에이전트 상태 모니터링 필요."
  * 규격: 수동 복귀는 `_needs_dispatch`를 세우고, 사용자 입력이 에이전트에 전달될 때 해제된다. 자동 복귀(무음·종료)는 세우지 않는다 — 사용자 의사 표시가 아니고, 비대화형 작업이 중간에 한 번 쉬었다고 영영 덮이지 않으면 곤란하기 때문이다.
  * 이 규칙이 D-011의 `MANUAL_WAKE_GRACE`(12초 유예)를 대체한다. 시간 기반 유예는 "읽는 중인지"를 추측할 뿐이지만, 새 지시가 왔는지는 확실한 신호다. 환경변수 `AMASK_WAKE_GRACE`는 제거했다.
  * **한계 (기록만)**: 비대화형 에이전트가 출력을 낸 뒤 오래 침묵하면(예: "Compiling..." 후 60초 무음) 유휴로 판정되어 복귀하고, 침묵이 이어지는 한 재진입하지 않는다. 무음이 y/n 대기인지 긴 작업인지 출력만으로는 구분할 수 없다.
* **D-015**: 레인 글리프를 **ASCII 자판 문자**로 한정하고 **한 칸 걸러** 떨어뜨림 (결정일: 2026-09-07)
  * 사용자 보고: 글자가 겹쳐 지저분하고, 일본 문자 대신 자판 문자를 원함.
  * 근거: 반각 가타카나(U+FF66~FF9D)는 규격상 1칸이지만 폰트와 터미널의 ambiguous-width 설정에 따라 2칸으로 그려진다. 그러면 옆 열을 침범해 화면이 뭉개진다. ASCII로 바꾸면 폭이 항상 1칸으로 확정된다.
  * 간격: `COLUMN_STEP = 2`. 글리프 옆에 항상 빈 열이 남아 cmatrix 특유의 성긴 질감이 나온다.
* **D-016**: 오버레이 중앙에 **음영 상태 패널** 표시 (결정일: 2026-09-07)
  * 사용자 요구: 프롬프트 / 에이전트 상태 / 가이드 노출. 이후 "하단 배치는 단절돼 보인다 → 중앙, 매트릭스에 융화", "박스 대신 텍스트 음영"으로 구체화.
  * 규격: 테두리 없이 배경 음영(256색 234번) 블록을 화면 중앙에 놓고, 레인에는 그 사각형만큼 **구멍(hole)**을 뚫어 겹치지 않게 한다. 드롭은 구멍을 통과해 아래에서 다시 나타나므로 패널이 레인 "앞"에 있는 것처럼 보인다.
  * 항목: 프롬프트(사용자가 입력한 마지막 줄), STATUS(작업 중/대기 + 스피너), MODEL, DIR, ELAPSED, TOKENS, OUTPUT(숨긴 출력 크기), 그리고 영문 가이드 `press any key to return`.
  * 프롬프트는 **메모리에만** 두고 스필 파일에 쓰지 않는다. 사용자가 친 내용을 파일로 남기면 FORBIDDEN(인증 토큰 유출)에 저촉될 수 있다.

  * D-032는 `Stop`에서 그 턴의 `prompt_id`를 기억하고 같은 id의 BUSY 이벤트를 낙오자로 버리도록 구현했다. 사용자 요청으로 조사 노트와 교차 확인하다가 **이미 더 나은 규칙이 정리돼 있었다는 것을 발견**했다.
  * 앞선 실측이 같은 현상을 이미 잡아 두었다(`Stop` 뒤 2.1~2.6초, `agent_type: ""`, `last_assistant_message`가 다음 프롬프트 제안). 정체는 이렇다 — Claude Code가 턴이 끝난 뒤 **이름 없는 내부 서브에이전트로 프롬프트 제안을 만들고** 그것이 `SubagentStop`으로 새어 나온다. 고칠 방향도 그때 이미 (a) `agent_id`를 실은 이벤트를 메인 상태에서 제외로 적혀 있었다.
  * Claude Code의 훅 규격이 공통 입력 필드에서 `agent_id`·`agent_type`을 **"`--agent`로 띄웠거나 서브에이전트 안에서 발화한 이벤트에만 있다"**고 정의한다. 즉 `agent_id`가 실려 있다는 것이 곧 "메인 스레드 상태가 아니다"의 규격상 표식이다.
  * 결정: BUSY로 매핑되는 이벤트가 `agent_id`를 실었으면 상태 판정에서 제외한다. `prompt_id` 대조와 `_stopped_prompt_id` 상태는 제거했다.
  * `prompt_id`로는 부족한 이유: 그 대조는 **직전에 끝난 턴**의 낙오자만 잡는다. 백그라운드 서브에이전트의 `PreToolUse`가 메인 `Stop` 뒤에 도착하는 경우까지 규칙 하나로 걸러지는 것은 `agent_id` 쪽이다. 이벤트 이름(`SubagentStop`)을 `EVENT_MEANING`에서 빼는 것보다도 넓다.
  * `EVENT_MEANING`은 그대로 둔다. 표는 이벤트의 의미를 적는 곳이고, "누구의 상태인가"는 페이로드가 답하는 별개의 축이다.
  * 정정: D-032 근거에 "`prompt_id`는 규격에 없는 필드"라고 쓸 뻔했으나 사실이 아니다. 「공통 입력 필드」에 정의되어 있고, 이벤트별 표에만 없다. 교체 이유는 필드의 문서화 여부가 아니라 **규칙의 범위**다.
  * 검증: `test_phase9_hooks.py` 신규 10개 항목. 수정을 되돌리면 5개가 실패한다(낙오자 재진입 `t=6.72`, 서브에이전트 툴 호출 재진입 `t=6.45`, 주입 마크업 표시, emitter의 `prompt_id`·`agent_id` 미전달). 실물 검증: `AMASK_DEBUG`를 켠 채 `bin/amask claude`를 pty로 구동해 실제 `claude`가 보낸 `prompt_id`가 러너까지 도달하는 것을 확인했다(`hook UserPromptSubmit -> busy prompt_id=2e9e172f-...`, 같은 id의 `Stop`).
  * 남은 것: 문서가 함께 제시한 (b) — 인터럽트에는 아무 훅도 발화하지 않아 걸린 BUSY의 유일한 탈출구가 `HOOK_STALL` 120초이고, 그래서 2분짜리 가짜 오버레이가 된다 — 는 손대지 않았다. 타이밍 상수와 합성 WAITING이 걸려 있어 이번 보고 범위 밖이다.

* **D-034**: 백그라운드 작업이 도는 중의 `Stop`도 WAITING으로 둔다 (결정일: 2026-09-09)
  * 사용자 관찰: 서브에이전트가 백그라운드로 도는데 사용자 프롬프트를 즉시 수행할 수 있는 상태가 있어 보인다. 맞다 — 실측으로 확인했고 트레이스를 아래에 남긴다.
  * 관측: `Agent` 툴이 띄운 서브에이전트가 `Bash`를 도는 구간(23.66~30.56) 안에서 후속 프롬프트가 27.37에 제출되고 29.93에 자기 `Stop`으로 닫혔다. 메인 턴과 백그라운드 작업이 같은 구간에 공존한다. `Stop`은 `background_tasks`로 그 시점에 살아 있는 작업 목록(`[{id, type: subagent|shell, status: running, description, ...}]`)을 실어 오고, 다 끝나면 `[]`가 된다.
  * 결정: **`background_tasks`가 비어 있지 않아도 `Stop`은 WAITING이다.** 오버레이를 걷고 사용자 입력을 받는다. 이 필드를 상태 판정에 쓰지 않는다.
  * 근거는 P-101(투명한 래퍼)이다. 그 시점 실제 claude는 프롬프트를 받는 상태이므로, 러너가 "작업 중"이라며 화면을 덮으면 래퍼가 실물보다 못한 것을 보여주게 된다. 백그라운드 완료 뒤에는 하네스가 알림을 프롬프트로 주입하고(`<task-notification>`, D-031) 그 턴의 `UserPromptSubmit`이 정상적으로 BUSY를 만들므로, 덮을 필요가 있는 구간은 그때 다시 온다.
  * 코드 변경 없음. 지금 구현이 이미 이렇게 동작한다 — 이 항목은 나중에 "백그라운드가 도는데 왜 안 덮나"가 나올 때의 근거다.
  * D-033을 다시 확인한 관측이 하나 있다. **서브에이전트 이벤트의 `prompt_id`는 자기를 띄운 턴이 아니라 발화 시점의 메인 프롬프트를 가리킨다** (`fd40bb66`이 띄운 서브에이전트의 툴 이벤트가 후속 턴 `6111a70f`을 실어 왔다). D-032의 `prompt_id` 대조는 이 트레이스에서 우연히만 맞는다 — 후속 턴이 살아 있는 동안 도착했다면 메인 상태로 새어 들어갔다. `agent_id` 규칙은 전부 옳게 걸렀다.
  * 남은 위험: WAITING 계열 이벤트에 `agent_id` 필터가 없다(`cli.py:423`은 BUSY만 검사). 이번 트레이스의 `Stop` 3건·`Notification` 1건 모두 `agent_id`가 없었고 서브에이전트의 턴 종료는 `SubagentStop`(BUSY, 필터됨)으로 왔으므로 비대칭 필터가 성립한다. 관측 한 번이고 문서 보장은 아니다 — WAITING에 `agent_id`가 실린 사례를 보면 그때 대칭으로 만든다.
  * `notification_type`의 `agent_completed`·`agent_needs_input`은 문서에 있지만 이번에 발화하지 않았다. 백그라운드 완료를 이 채널로 알 수는 없다.

* **D-035**: `Stop` 이후 WAITING 구간은 백그라운드 작업이 남아 있어도 덮지 않는다 — 사용자 지시 (결정일: 2026-09-09)
  * 사용자 지시: "사용자의 프롬프트를 즉시 실행할 수 있는 `Stop`이 온 이후에는 matrix로 가리면 안 됨."
  * 근거는 관측으로 뒷받침된다. `Stop`이 온 시점부터 입력창은 실제로 동작한다 — `background_tasks`에 서브에이전트가 `running`으로 남아 있어도 그 사이 제출한 프롬프트는 새 `prompt_id`로 자기 턴을 열고 완주했다(2026-09-09 트레이스, 23.66~30.56 구간 안의 27.37 제출 → 29.93 `Stop`). 이 구간을 덮으면 러너가 **동작하는 입력창을 숨긴다.** P-101 위반이고, SC-003이 말하는 "사용자 개입을 기다리는 상태"와 같은 성질이다.
  * **문장의 범위를 좁혀 읽었다.** 문자 그대로면 첫 `Stop` 이후 영구히 덮지 못하므로 스크린세이버가 죽는다. 규칙은 "`Stop`을 받고 새 턴이 열리기 전까지의 WAITING 구간"에 적용된다. 새 턴은 `UserPromptSubmit`으로 시작하고, 이때는 주입된 알림이 연 턴도 포함한다 — 뒤에 실제 작업이 따라오므로(D-031) 그 구간은 덮는 것이 맞다.
  * 코드 변경 없음. 현재 구현이 이미 이 규칙을 만족한다. `_should_cover`는 `_busy_since`가 있어야 참이고, WAITING 이벤트는 `_busy_since`를 지우며 `_tick`도 훅이 WAITING을 말하는 동안 매 사이클 지운다. `_hooks_speaking()`이 WAITING을 만료시키지 않으므로(BUSY만 `HOOK_STALL`을 탄다) 덮기로 돌아갈 경로가 없다.
  * D-034를 규격으로 승격한 것이다. D-034는 "`bg`가 비어 있지 않은 `Stop`도 WAITING으로 둔다"는 판정이었고, 이 항목은 그것을 **덮지 않는다는 요구사항**으로 고정한다. 앞으로 백그라운드 작업을 상태 판정에 넣자는 변경은 이 항목을 먼저 뒤집어야 한다.
  * 검증: `test_phase9_hooks.py`에 4개 항목 추가. `Stop(background_tasks 있음)` 뒤 서브에이전트 이벤트가 계속 오고 11초가 지나도 재진입이 없음(`OVERLAY_DELAY`를 1.5초로 조여 8회분 여유), 그리고 주입된 알림이 연 턴은 여전히 덮음. **역대조**로 확인했다 — `WAITING` + `background_tasks` 비어 있지 않음을 BUSY로 바꾸는(D-034가 기각한 방향) 패치를 임시로 넣으면 두 항목이 `t=3.02`·`t=2.52`에 실패하고, 되돌리면 통과한다.
  * 미해결: `Stop`이 오지 않는 경로는 이 규칙으로 덮이지 않는다. 인터럽트에는 아무 훅도 발화하지 않으므로(실측) WAITING 구간이 시작되지도 않고 `HOOK_STALL` 120초까지 덮인 채로 남는다. 규칙을 만족시키려면 그쪽은 별도 작업이다 — 실측 문서의 (b) 항목이 그것이다.

* **D-036**: 인터럽트는 감지하지 않고, 사용자가 이번 턴을 건너뛰는 키를 준다 — 사용자 지시 (결정일: 2026-09-09)
  * 문제: 응답 중 인터럽트(ESC)에는 **어떤 훅도 발화하지 않는다** — `Stop`도 `StopFailure`도 `Notification`도. 실측으로 확인했다. 걸린 BUSY를 풀어줄 이벤트가 없어 `HOOK_STALL` 120초까지 유휴 프롬프트 위에 레인이 덮인다.
  * 검토하고 **기각한 방향들**:
    * *무음 override* — 전체 화면 에이전트는 작업 중에도 최대 2.13초 무음이 실측됐다. 무음으로 인터럽트를 판정하려면 임계값이 필요하고, 오판하면 에이전트가 아직 쓰고 있는데 화면이 걷힌다. D-025가 훅을 도입한 이유가 정확히 이 구분이므로 되돌리는 셈이다. 게다가 긴 툴 호출 구간의 공백은 아직 재지 못했다(문서의 미해결 항목).
    * *ESC 키 판별* — 사용자 지적으로 기각. ESC·Ctrl+C는 문맥에 따라 다르게 동작한다. 응답 중 인터럽트가 되기도 하고, **응답과 무관하게 작성 중인 프롬프트 초안만 취소**하기도 한다. 후자를 인터럽트로 오판하면 스트리밍 중에 WAITING이 걸리고, D-030에 따라 WAITING은 만료되지 않으므로 툴 호출 없는 응답에서는 `Stop`까지 화면이 걷힌 채 남는다. `InputLine`의 초안 유무로 가르는 안도 검토했으나, 그건 입력창의 **재구현**이라 ESC가 초안을 리셋하지 않는 기존 구멍과 히스토리 소환·붙여넣기 미모델링으로 드리프트한다.
  * 결정: **감지하지 않는다.** 덮여 있는 동안 `q`를 누르면 깨어나고 그 턴 동안 다시 덮지 않는다. 다음 프롬프트 제출에서 자동 해제된다 — 훅이 있으면 `UserPromptSubmit`, 없으면 `InputLine`의 제출 감지가 경계다.
  * **`q`가 덮인 동안에만 유효한 것이 핵심이다.** 덮인 중 사용자 바이트는 이미 전부 버려지므로(D-008/SC-002 — 깨우려 누른 Enter가 빈 프롬프트를 제출하면 안 된다) `q`를 러너가 쓰는 비용이 0이고 D-008도 그대로다. 걷힌 상태에서는 모든 바이트가 에이전트로 전달되므로, 거기서 `q`를 가로채면 사용자가 입력 중인 글자를 먹는다(P-101).
  * `_wake()`는 "A keypress buys reading time, not a permanent dismissal"을 약속한다. `q`는 그 약속의 **의도적 예외**이고 다른 모든 키에는 여전히 유효하다.
  * 함께 넣은 표시: 훅이 BUSY라고 하는데 출력이 `IDLE_HINT_AFTER`(10초) 이상 없으면 패널의 `q` 힌트를 강조한다(`idle? q to skip now`). **이 임계값은 표시만 바꾼다** — 상태 판정에 닿지 않으므로 오판의 비용이 "힌트가 필요보다 크게 나온 것"뿐이다. 그래서 상태용 임계값은 거부하면서 이것만 남겼다. env 노브로 노출하지 않는다(README 「타이밍 조정」은 상태를 결정하는 세 상수의 자리다). 두 힌트 문자열은 길이를 같게 맞춰 패널이 흔들리지 않게 했다.
  * 검증: `test_phase9_hooks.py`에 9개 항목(q 억제, 다른 키는 억제 안 함, 새 프롬프트에서 해제, `q`가 에이전트로 새지 않음, 힌트 폭 일치, 강조 유무, 행 수 불변, `_tick`이 `_idle_suspected`를 상태 판정에 쓰지 않음). `hooked_seq.py` 픽스처에 stdin 에코를 넣어 D-008을 부재로 검증할 수 있게 했다.

* **D-037**: 오버레이는 `ESC[2J`(ED 2)를 쓰지 않는다 — 행별 `ESC[2K`(EL)로 지운다 (결정일: 2026-09-10)

* **D-039**: 세션마다 로컬 제어 소켓을 연다 — 외부 앱이 상태를 읽고 세 상수를 세션별로 바꾼다 (결정일: 2026-09-17)

  * 사용자 지시: "화면 높이가 짧은 경우 짤리고 네비게이션이 안되네." 상세 화면(D-043)에서 나온 지적이지만, **목록도 같은 버그였다** — `_draw`가 `height - 2`에서 그리기를 멈출 뿐이라 세션이 창보다 많으면 뒤쪽은 존재조차 보이지 않았고, 커서를 그리로 옮겨도 화면은 따라가지 않았다. 상세만 고치면 같은 신고가 목록에서 다시 온다.
  * **목록은 커서를 가운데에 두고 따라간다**(`visible_span`). "최소한으로만 스크롤"이 눈에는 더 편하지만 그러려면 직전 스크롤 위치를 알아야 하는데, 이 뷰는 0.5초마다 `started` 순으로 재정렬되는 목록을 **매번 처음부터 다시 그린다** — "지난번에 어디였는지"는 이 뷰가 가진 적 없는 정보다. 커서 위치만으로 결정되는 규칙이 재정렬을 만나도 어긋나지 않는다.
  * **상세는 오프셋을 들고 `_draw_detail`이 깎아서 돌려준다.** 클램프를 그리는 쪽에 둔 이유는 접힌 줄 수가 창 너비에 달려 있어서다 — 루프는 너비를 모르는 채로 키를 받는다. 덕분에 `G`(끝)는 큰 수를 넣기만 하면 되고, 바닥에서 `j`를 눌러도 값이 부풀지 않아 `k` 한 번에 다시 올라온다.
  * 키는 상세에서만 다르다: `↑↓`/`jk` 한 줄, `space`/`b`/PgUp·PgDn 한 쪽, `g`/`G` 처음·끝. 목록에서 세션을 고르던 키가 상세에서는 본문을 움직인다 — 상세에는 세션이 하나뿐이라 이동 키가 할 일이 없고, 짧은 창에서 사람이 가장 먼저 누르는 키가 그것이다.
  * **잘린 것과 원래 짧은 것을 구분해 준다**: 제목 오른쪽에 `↑3 ↓12`. 이것이 없으면 짧은 창은 "내용이 이게 다"와 구분되지 않는다 — 이번 신고의 절반이 그 혼동이다.
  * 프레임은 자기 몫으로 네 줄(제목·헤더·응답·키 안내)을 쓰고 나머지가 본문이다(`body_capacity`). 메시지가 없어도 그 줄을 비워 두는 쪽을 골랐다 — 있을 때만 접으면 응답 한 줄에 스크롤 기하가 흔들린다.
  * 검증: `test_phase10_control.py`에 항목 추가 — 순수 함수(`body_capacity`/`visible_span`/`clamp_offset`/`more_marker`), 20개 중 어느 커서 위치에서도 커서가 화면 안에 있는지, 그리고 pty에서 높이 8의 상세·긴 목록의 위/아래 프레임.
* **D-046**: `--top` 목록의 열 폭을 고정하지 않고 **내용에 맞춰 잰다** (결정일: 2026-09-21)
  * 사용자 보고: "상태 너비가 너무 좁고, 폴더가 짤려." D-044에서 고정 폭 `(1, 7, 4, 20, 5, 18)`을 그대로 물려 썼는데, 상태는 깃발이 다 붙으면 `작업·건너뜀·유휴의심·훅없음` 27셀이라 20에서 잘렸고 폴더는 저장소 이름 하나가 18셀을 넘겼다. **하필 할 말이 있는 행만 잘리는** 폭이었다.
  * 그려질 행을 먼저 만들고, 각 열을 그 열에 실제로 든 내용(헤더 포함)의 최대 폭으로 잡는다(`column_widths`). 폭이 모자라면 **바닥에서 가장 멀리 떨어진 열부터** 한 셀씩 깎는다 — 긴 폴더 이름이 이미 빠듯한 열보다 먼저 양보하는 것이 맞다.
  * 바닥(`MIN_WIDTH`)과 천장(`MAX_WIDTH`)을 둔다. 바닥이 없으면 좁은 창에서 열이 사라지고, 천장이 없으면 긴 이름 하나가 프롬프트를 밀어낸다. 프롬프트에는 `PROMPT_FLOOR`(16셀)를 항상 남긴다 — 행이 존재하는 이유가 프롬프트라, 마지막까지 지켜야 하는 것은 이쪽이다.
  * 폴더는 여전히 경로의 마지막 한 칸만 보여준다(D-044). 바뀐 것은 그 한 칸이 잘리지 않는다는 것뿐이고, 전체 경로는 상세 화면에 있다.
  * 검증: `test_phase10_control.py`에 `column_widths` 순수 함수 검사(깃발 전부 붙은 상태·긴 폴더 미절단, 짧은 내용에는 자리를 덜 줌, 좁은 창 축소, 바닥 준수)와 140칼럼 실제 프레임 검사를 추가했다.

* **D-048**: GitHub Actions로 스위트를 Linux·macOS × Python 3.11~3.13에서 돌린다 (결정일: 2026-09-22)
  * 사용자 지시("ci 추가"), 범위는 확인 후 6잡 매트릭스로 정했다. 설치 단계도 캐시도 없다 — 표준 라이브러리만 쓰므로(D-006) 해결할 의존성이 없고, 그 사실이 매트릭스를 싸게 만든다.
  * **macOS를 넣은 이유**: 지금까지의 모든 실측이 macOS + iTerm2에서 나왔고(PROJECT_STATE 전반), pty·termios 동작은 커널에 딸린다. Linux만 돌리면 개발 환경이 검증되지 않고, macOS만 돌리면 이 프로젝트가 한 번도 확인해 본 적 없는 플랫폼을 계속 확인하지 않는다.
  * `fail-fast: false` — 한 조합의 실패가 나머지를 취소하면 "macOS만 깨졌는가, 3.11만 깨졌는가"를 다시 돌려서 알아내야 한다. 그 구분이 이 매트릭스의 목적이다.
  * `concurrency` + `cancel-in-progress` — 스위트가 실제 pty를 띄우고 한 번에 몇 분씩 걸리므로, 밀린 중복 실행은 낭비다.
  * **아직 검증되지 않은 것**: Linux에서 스위트를 돌린 적이 없다. 타이밍 단정(0.2초 복귀, 0.7초 지연 진입 등)이 러너 성능에 걸려 흔들릴 수 있다. 첫 CI 실행 결과를 보고 판단할 일이며, 그때 필요하면 임계값이 아니라 `AMASK_*` 환경변수로 스위트 쪽을 늦추는 방향을 먼저 본다.
